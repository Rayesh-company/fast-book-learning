# ورود با پیامک (OTP): وضعیت فعلی و راهنمای اتصال به هر سامانهٔ پیامک دیگری

این داکیومنت دو کار می‌کند: اول نشان می‌دهد در ِ ورودِ پیامکی الان دقیقاً چطور به پنل وصل است، و دوم یک راهنمای گام‌به‌گام است برای هر روزی که بخواهید فرستندهٔ پیامک را به پلتفرم دیگری ببرید — بدون آنکه چیز دیگری در پروژه دست بخورد.

همهٔ کد درگیر در سه فایل است:

| فایل | نقش |
|---|---|
| `ui/otp.py` | کل لایهٔ OTP: ساخت کد، محدودیت‌ها، **و تنها نقطهٔ تماس با پنل پیامک** |
| `ui/serve.py` | دو مسیر HTTP: `POST /auth/otp/request` و `POST /auth/otp/verify` (خطوط ۲۵۱۰ تا ۲۶۰۶) |
| `ui/throttle.py` | بودجهٔ هر IP روی هر دو در (خطوط ۴۱ و ۴۲) |

کلاینت موبایل (`requestOtp` / `verifyOtp`) فقط با این دو مسیر HTTP حرف می‌زند و **از هویت پنل بی‌خبر است** — تعویض پنل هیچ تغییری در اپ نمی‌خواهد و نیاز به بیلد یا OTA ندارد.

---

## ۱) الان چطور فعال است

### جریان کامل یک ورود

1. کاربر شماره را می‌زند؛ کلاینت `POST /auth/otp/request` با `{"phone": "09…"}` می‌زند.
2. سرور شماره را با `normalize_local_phone` به شکل محلی ایرانی (الگوی `09\d{9}`) می‌رساند؛ غیر از آن ۴۰۰.
3. `ui/otp.py::request_otp` به این ترتیب کار می‌کند: **اول** سهمیه‌ها را چک می‌کند، **بعد** کد شش‌رقمی تصادفی می‌سازد و از طریق پنل می‌فرستد، **آخر** کد را در حافظه ثبت می‌کند. اگر ارسال شکست بخورد هیچ‌چیز ثبت نمی‌شود — یعنی خطای پنل نه سهمیهٔ روزانه می‌سوزاند نه کاربر را در گیرِ «دو دقیقه صبر کن» می‌اندازد.
4. کاربر کد را می‌زند؛ `POST /auth/otp/verify` با `{"phone", "code"}`.
5. مقایسه در زمان ثابت (`secrets.compare_digest`)؛ جواب منفیِ «کد غلط»، «کد منقضی» و «سقف تلاش» از نظر پاسخ HTTP یکسان است (۴۱) تا حدس‌زننده چیزی نفهمد.
6. کد درست = مالکیتِ ثابت‌شدهٔ سیم‌کارت. حسابِ موجود با آن شماره (`account_by_phone`، تطبیق روی ۱۰ رقم آخر) یا حسابِ خودساخته (`signup_phone_account`: ایمیلِ `09…@phone.local`، نقش `operator`) — توکن و کوکی همان پاسخ `/auth/login`.

### قوانین و سقف‌ها (در سورس پین شده، مستقل از پنل)

| قانون | مقدار | کجا |
|---|---|---|
| عمر کد | ۳۰۰ ثانیه | `OTP_TTL_SECONDS` |
| فاصلهٔ ارسال مجدد | ۱۲۰ ثانیه | `OTP_RESEND_SECONDS` |
| حداکثر حدس غلط | ۵ بار، بعد کد می‌میرد | `OTP_MAX_ATTEMPTS` |
| سهمیهٔ روزانهٔ هر شماره | ۱۰ پیامک | `OTP_DAILY_PER_PHONE` |
| بودجهٔ هر IP روی هر در | ۳۰ درخواست در ۱۵ دقیقه | `throttle.OTP_REQUESTS` / `OTP_VERIFIES` |

کدها **فقط در حافظه‌اند** (یک دیکشنری با قفل، `_Codes`): ری‌استارت یعنی درخواست کد تازه؛ هیچ کدی هرگز روی دیسک نمی‌نشیند.

### پنل فعلی: فراز اسمس

پنل فعلی «فراز اسمس» است که از طریق وب‌سرویس `api.iranpayamak.com` (همان API که farazsms.com مستند می‌کند) کار می‌کند. قانون ایران: پیامک OTP فقط باید روی **الگو (pattern)** ثبت‌شده در پنل برود — متن پیام در پنل اپراتور زندگی می‌کند، نه در این ریپو؛ ما فقط کد را داخل متغیرِ الگو می‌ریزیم.

تنها تابعی که با پنل حرف می‌زند `send_otp_sms(phone, code)` در `ui/otp.py` است — یک POST به:

```text
POST https://api.iranpayamak.com/ws/v1/sms/pattern
Api-Key: <کلید خام>
{
  "code": "<کد الگو>",
  "attributes": {"<نام متغیر>": "<کد شش‌رقمی>"},
  "recipient": "09123456789",     ← شکل محلی ۰۹…، نه +98 (پنل +98 را رد می‌کند)
  "line_number": "<خط فرستنده>",
  "number_format": "english"
}
```

نکتهٔ مهم رفتاری: این پنل بعضی ردها را با **HTTP 200 و `{"status": "error"}`** جواب می‌دهد؛ کد ما پیکر را هم قضاوت می‌کند، نه فقط وضعیت HTTP را — چون ورودی که در صف نرفته نباید «فرستاده‌شده» به نظر برسد.

### چهار متغیر محیطی و مسیرشان تا سرور

| متغیر | معنی |
|---|---|
| `FARAZSMS_API_KEY` | کلید API از پنل ← تنظیمات ← دسترسی API |
| `FARAZSMS_PATTERN_CODE` | شناسهٔ الگوی OTP که در پنل ثبت شده |
| `FARAZSMS_FROM_NUMBER` | خط فرستنده (لیست خطوط: `GET /ws/v1/lines/accessible`) |
| `FARAZSMS_PATTERN_PARAM` | نام متغیرِ کد داخل الگو — **به الگویی که ثبت کرده‌اید بستگی دارد، نه به ما** |

مسیر مقادیر: GitHub Secrets ← مرحلهٔ deploy در `.github/workflows/ci.yml` (upsert در فایل `.env` روی سرور، با کوتیشن تکی) ← `compose.yaml` (خطوط ۳۰۶–۳۰۹) به کانتینر می‌رساند ← `ui/otp.py` هنگام import می‌خواند.

⚠️ دامِ واقعی که یک‌بار گرفتیم: در سورس پیش‌فرضِ `FARAZ_PATTERN_PARAM` مقدار `codeotp` است، اما الگویی که روی پنلِ پروداکشن ثبت شده (`gKNR73mwli`) متغیرش `%codes%` نام دارد — CI همان `codes` را در `.env` می‌نویسد. **نام متغیر الگو را از تعریف الگو در پنل خودتان بخوانید، نه از سورس.**

اگر حتی یکی از سه متغیر اول ست نباشد، `configured()` نادرست برمی‌گرداند و هر دو درِ OTP با **۵۰۳ صادقانه** جواب می‌دهند — پنلِ نیمه‌تنظیم هرگز پیامک خراب نمی‌فرستد.

## ۲) قراردادی که هر پنل جدید باید حفظ کند

کل سیستم فقط یک قرارداد را از فرستنده می‌خواهد؛ هر چیزی بیرون از این قرارداد جای خودش را عوض نمی‌کند:

1. **`send_otp_sms(phone: str, code: str)`** — تنها نقطهٔ تماس. موفق: هیچ برنمی‌گرداند. شکست (ردِ پنل، قطع شبکه، تایم‌اوت، ۲۰۰ِ دروغین): استثنای `OtpSendFailed` پرتاب می‌کند — همین استثناست که ۵۰۲ می‌سازد و باعث می‌شود ارسالِ ناموفق چیزی از سهمیه‌ها کم نکند.
2. **`configured() -> bool`** — آیا همهٔ حقایقِ لازمِ پنل جدید ست شده؟ ست نباشد = ۵۰۳.
3. شماره‌ای که به تابع می‌رسد همیشه **شکل محلی `09xxxxxxxxx`** است؛ اگر پنل جدید فرمت دیگری (مثلاً `+98…` یا `98…`) می‌خواهد، تبدیل **داخل** `send_otp_sms` انجام شود — بقیهٔ سیستم با شکل محلی حرف می‌زند.
4. کد فقط از سیم پیامک بیرون می‌رود — نه در لاگ، نه در پاسخ HTTP، نه هیچ‌جا.

جدول رفتار HTTP که باید دست‌نخورده بماند (کلاینت موبایل و برنامک به آن تکیه کرده‌اند):

| وضعیت | پاسخ |
|---|---|
| بدنه/شمارهٔ نامعتبر | ۴۰۰ |
| زودتر از کوول‌داون یا سهمیهٔ روزانه | ۴۲۹ |
| پنل تنظیم نیست | ۵۰۳ |
| پنل رد کرد یا جواب نداد | ۵۰۲ |
| کد غلط/منقضی/سقس تلاش (هر سه یکسان) | ۴۰۱ |
| موفق | ۲۰۰ + بدنهٔ `{"email","role","token"}` + کوکی HttpOnly |

## ۳) گام‌به‌گام: اتصال به پلتفرم جدید

### گام ۱ — از پنل جدید این هفت چیز را جمع کنید

پیش از هر تغییری در کد، این‌ها را از مستندات/پنلِ پلتفرم جدید دربیاورید:

1. **URL و متد** ارسال (خیلی از پنل‌ها GET با پارامتر دارند، خیلی‌ها POST/JSON).
2. **نوع احراز**: کلید در هدر (با چه نامی؟)، در مسیر URL، یا در بدنه؟
3. **الگو**: آیا OTP باید روی الگوی ثبت‌شده برود؟ (در ایران بله — قانون است.) پس: کد الگو + **نام متغیر کد داخل الگو** + فرآیند تأیید الگو در پنل.
4. **خط فرستنده** و اینکه از قبل فعال است یا باید فعالش کنید.
5. **فرمت شمارهٔ گیرنده**: محلی `09…`، یا `+989…`، یا `989…`.
6. **گویش پاسخ**: موفقیت/خطا را با کد HTTP می‌گوید یا با ۲۰۰ + پرچم در پیکر؟ (خیلی رایج است که ۲۰۰ِ خالیِ دروغین داشته باشند.)
7. شماره‌گذاری/اعتبار پنل و محدودیت‌های خودش.

### گام ۲ — `ui/otp.py` را بازنویسی کنید (فقط بخش پنل)

سه کار در همین فایل:

- چهار ثابت `FARAZ_*` را با متغیرهای محیطی پنل جدید جایگزین کنید (نام‌گذاری به شما؛ الگوی `SMSVENDOR_API_KEY` و امثال آن خوانا است).
- `configured()` را به حقایقِ لازمِ پنل جدید گره بزنید.
- بدنهٔ `send_otp_sms` را بازنویسی کنید — URL، احراز، فرمت شماره، و قضاوتِ پاسخ. قلب تابع همیشه این ساختار است:

```python
def send_otp_sms(phone: str, code: str) -> None:
    # ۱) بدنه/هدر/URL را به گویش پنل جدید بسازید
    # ۲) اگر پنل +98 می‌خواهد، همین‌جا تبدیل کنید:
    #    e164 = "+98" + phone[1:]
    # ۳) بفرستید (همان seam ماژول‌سطح urlopen بماند تا تست‌ها نفس بکشند)
    # ۴) موفقیت را *از پاسخ پنل* قضاوت کنید، نه فقط از کد HTTP؛
    #    هر شکست:  raise OtpSendFailed(...)
```

**مثال کامل** — شکل یک فرستندهٔ کاملاً متداول (سبک کاوه‌نگار؛ هنگام اجرا با مستندات پنل خودتان تطبیق دهید):

```python
# پنل فرضی «X»: GET، کلید داخل URL، الگو با یک متغیر به نام token
KAVEH_SEND_URL = "https://api.example-sms.ir/v1/{key}/verify/lookup.json"

def send_otp_sms(phone: str, code: str) -> None:
    url = KAVEH_SEND_URL.format(key=VENDOR_API_KEY)
    query = urllib.parse.urlencode({
        "receptor": "+98" + phone[1:],       # این پنل E.164 می‌خواهد
        "token": code,                        # نام متغیرِ الگوی این پنل
        "template": VENDOR_TEMPLATE,          # کد الگو
    })
    request = Request(f"{url}?{query}", headers={"Accept": "application/json"})
    body = urlopen(request, timeout=15).read()
    try:
        verdict = json.loads(body).get("return", {}).get("status")
    except (ValueError, AttributeError):
        verdict = None
    if verdict != 200:                        # این پنل موفقیت را در پیکر می‌گوید
        raise OtpSendFailed(body[:200].decode("utf-8", "replace"))
```

بقیهٔ `ui/otp.py` — `request_otp`، `verify_otp`، کلاس `_Codes`، همهٔ سقف‌ها — **دست نمی‌خورد**: آن‌ها به پنل مربوط نیستند.

### گام ۳ — لولهٔ متغیرهای محیطی

1. `compose.yaml` (خطوط ۳۰۶–۳۰۹): نام متغیرهای فراز را با نام‌های جدید عوض کنید.
2. `.github/workflows/ci.yml`: در GitHub Secrets مقادیر جدید را بسازید و در مرحلهٔ «Upsert … into the box .env» نام‌ها را عوض کنید (خطوط ۲۱۶–۲۳۸). `FARAZSMS_PATTERN_PARAM 'codes'` سخت‌کد‌شده در این مرحله را هم به نام متغیرِ الگوی جدید تغییر دهید.
3. مقادیر قدیمی `FARAZSMS_*` را از Secrets و `.env` سرور حذف کنید تا پنلِ مرده همیشه ۵۰۳ صادقانه بماند، نه خطای پنهان.

### گام ۴ — تست‌ها را به گویش پنل جدید گویند

`tests/test_otp_login.py` با یک پنلِ قلابی (fake) که `otp.urlopen` را می‌پوشاند، همهٔ جریان را بدون شبکه و بدون هزینه تست می‌کند (خطوط ۹۶–۱۰۰). سه چیز در فیکسچر به پنل جدید وابسته است: نام متغیرها، شکل بدنه/پاسخ، و شکل شماره. گویش فیکسچر را به پنل جدید برگردانید — تست‌های رفتاری (کوول‌داون، ۴۱ِ یکسان، سقف روزانه، خودثبتیِ حساب) باید بدون تغییر سبز بمانند؛ اگر جایی به پنل گره خورده‌اند، آن‌جا دقیقاً همان نقطه‌ای است که قراردادِ بخش ۲ را شکسته‌اید.

### گام ۵ — استقرار و پروب زنده

```bash
# بدون شبکهٔ واقعی، کل رفتار:
python -m pytest tests/test_otp_login.py tests/test_throttle.py -q

# روی سرور، بعد از deploy — درِ تنظیم‌نشده دیگر نباید ۵۰۳ بدهد:
curl -s -X POST https://<host>/auth/otp/request \
  -H 'Content-Type: application/json' -d '{"phone":"09xxxxxxxxx"}'
```

سپس با **شمارهٔ خودتان** یک ورود واقعی بزنید و لاگ کانتینر session را ببینید. اگر پنل جدید ترازو/مانده دارد، قبل و بعد را در پنل خودش چک کنید.
